Blackhole: native Kazoo WebSocket integration

Source-reviewed contract, not deployment certification. Blackhole provides Kazoo's AMQP-to-WebSocket event transport. The account-scoped live queue HTTP snapshots and exact queue invalidation namespace below are implemented in source, not certified live by this catalog. Historical reporting, durable replay and gap-free resynchronization are not provided.

Endpoints and OpenAPI representation

  • GET /v2/websockets: configured binding discovery. This exact top-level route is public in the source. Missing/empty data is not proof that no events exist; configuration and running modules must be checked.
  • GET /v2/accounts/{ACCOUNT_ID}/websockets and /{SOCKET_ID}: session inspection, not subscription endpoints. These retain separate upstream contract/authorization review limitations.
  • wss://<trusted-kazoo-host>/websocket: the installer reverse-proxy endpoint. It is not /v2/websocket. Native Blackhole defaults to port 5555. On a separate UI server configure its proxy upstream to the apps server, or configure a trusted WSS endpoint explicitly. Do not assume the Next.js server itself hosts Blackhole.

The OpenAPI document includes the HTTP upgrade/discovery operations, reusable Blackhole* message schemas, and the x-blackhole extension linking client/server messages. OpenAPI 3.0 describes HTTP, not a complete WebSocket session: generated HTTP SDKs do not automatically implement these frames. No fictitious POST subscribe endpoint is provided. This page is the companion protocol/lifecycle reference; it is not an AsyncAPI specification.

Authentication and connection

Obtain an account-scoped auth_token through Crossbar HTTPS authentication. HTTP APIs use X-Auth-Token; browser WebSocket commands use the JSON auth_token field. Browser WebSocket constructors cannot set arbitrary HTTP headers. This source rejects WebSocket subprotocols, so do not pass the token as a second constructor argument. Never put credentials in query strings, examples, logs or committed frontend configuration.

An anonymous HTTP upgrade can succeed; 101 Switching Protocols alone proves neither authentication nor subscription. Send an authenticated command and require its matching successful reply. The recommended client schemas deliberately require a token and a correlation ID on every command, although the server allows some omissions.

Security acceptance still required: the generic call namespace caches authenticated socket context. Sending a new token there does not reliably switch identity or prove expiry/revocation has been enforced for existing subscriptions. The dedicated queue-live namespace instead uses fresh token and resource authorization at subscription and coalesced delivery, as described below; native token caches still prevent any instant-global-revocation claim. Close and reconnect on logout, account/user/token changes or expiry. Client cleanup is not a substitute for server-side expiry, revocation, resource-scope and tenant-isolation tests. Generic account hierarchy authorization alone does not grant queue-live access.

JSON command examples

These generic call examples are illustrative frames, not executed by this page. Replace placeholders in your own authenticated client. Send exactly one of binding or bindings. In the generic path a supplied bindings array takes precedence; queue-live rejects mixed fields and multiple bindings.

{
  "action": "subscribe",
  "auth_token": "<TOKEN_FROM_YOUR_AUTH_FLOW>",
  "request_id": "frontend-subscribe-1",
  "data": {
    "account_id": "<ACCOUNT_ID>",
    "bindings": ["call.CHANNEL_CREATE.*", "call.CHANNEL_ANSWER.*", "call.CHANNEL_DESTROY.*"]
  }
}

Account omission defaults to the authenticated account. Request only necessary events and discover supported patterns first. For a single call, replace the final * with its actual call ID. Supported event families depend on loaded modules; a generic call event is not a queue-agent state event.

{"action":"reply","request_id":"frontend-subscribe-1","status":"success",
 "data":{"subscribed":["call.CHANNEL_CREATE.*","call.CHANNEL_ANSWER.*","call.CHANNEL_DESTROY.*"],
         "subscriptions":["call.CHANNEL_CREATE.*","call.CHANNEL_ANSWER.*","call.CHANNEL_DESTROY.*"]}}

{"action":"event","subscribed_key":"call.CHANNEL_ANSWER.*",
 "subscription_key":"call.<ACCOUNT_ID>.CHANNEL_ANSWER.*",
 "name":"CHANNEL_ANSWER","routing_key":"call.<ACCOUNT_ID>.CHANNEL_ANSWER.<CALL_ID>",
 "data":{"call_id":"<CALL_ID>"}}

The event above illustrates the envelope, not a complete typed call payload. Data is event-specific and normalized. Do not assume every event contains a queue ID, timestamp or globally unique event identifier. Subscription results use arrays; an already present subscription can return an empty subscribed array. Always inspect subscriptions and correlate request_id.

{"action":"ping","auth_token":"<TOKEN_FROM_YOUR_AUTH_FLOW>","request_id":"frontend-ping-1"}
{"action":"reply","request_id":"frontend-ping-1","status":"success","data":{"response":"pong"}}

{"action":"unsubscribe","auth_token":"<TOKEN_FROM_YOUR_AUTH_FLOW>","request_id":"frontend-unsubscribe-1",
 "data":{"account_id":"<ACCOUNT_ID>","bindings":["call.CHANNEL_CREATE.*","call.CHANNEL_ANSWER.*","call.CHANNEL_DESTROY.*"]}}

Unsubscribe replies contain unsubscribed and subscriptions arrays. Empty unsubscribe is rejected in this source; retain the explicit binding list, or close the connection to release all its subscriptions. An error reply contains status: "error" and data.errors; handle it as failure, not as an acknowledgement. JSON ping/pong is application-level health, distinct from protocol control frames and from call/queue health.

Next.js client lifecycle

Exact queue-live invalidation — implemented in source, not live-deployed

Use GET /v2/accounts/{ACCOUNT_ID}/queues/live for bounded overview pages and GET /v2/accounts/{ACCOUNT_ID}/queues/{QUEUE_ID}/live for selected detail. Inspect explicit availability and source coverage; null is unknown, not zero. Detail exposes bounded call and authorized roster/runtime observations, not caller PII, actual queue positions or ready-to-ring eligibility. The public websocket_updates capability is a separate rollout decision; this static contract does not enable it.

{"action":"subscribe","auth_token":"<TOKEN_FROM_YOUR_AUTH_FLOW>","request_id":"queue-subscribe-1",
 "data":{"account_id":"<ACCOUNT_32_LOWER_HEX>","binding":"queue_live.changed.<QUEUE_32_LOWER_HEX>"}}

{"action":"reply","request_id":"queue-subscribe-1","status":"success",
 "data":{"subscribed":["queue_live.changed.<QUEUE_32_LOWER_HEX>"],
         "subscriptions":["queue_live.changed.<QUEUE_32_LOWER_HEX>"]}}

{"action":"event","name":"changed","subscribed_key":"queue_live.changed.<QUEUE_32_LOWER_HEX>",
 "subscription_key":"acdc.dashboard.changed.<ACCOUNT_32_LOWER_HEX>.<QUEUE_32_LOWER_HEX>",
 "routing_key":"acdc.dashboard.changed.<ACCOUNT_32_LOWER_HEX>.<QUEUE_32_LOWER_HEX>",
 "data":{"version":1,"account_id":"<ACCOUNT_32_LOWER_HEX>","queue_id":"<QUEUE_32_LOWER_HEX>"}}

Account is explicit; account and queue IDs are exactly 32 lowercase hexadecimal characters. Send one binding or one-element bindings array, never both, never a wildcard. Wait for each matching successful request_id before the next subscribe. One authorization worker per socket has a 3-second result deadline; at most 100 subscriptions and 100 coalesced dirty scopes are retained. A busy/error reply is not success. Unsubscribe uses the same exact scope and returns unsubscribed plus remaining subscriptions; retain these bindings for cleanup.

Subscribe and each coalesced delivery require fresh token validation through active local Crossbar authority, the live/queues/stats permissions and a nondeleted tenant-owned selected queue. Generic hierarchy access is insufficient. Worker results recheck token identity and subscription generation; no token is stored in broker binding payloads. Standalone Blackhole without local authority fails closed. This preserves native token-provider cache policy; deployment/expiry/isolation acceptance is still required.

The event data is closed: only version, account_id and queue_id. Match the account, queue and all routing fields to the active registration before refetching. Do not count events or merge them as deltas. A subscribe ACK is not a broker-ready barrier. Hints can be lost through overload, binding races, broker/federation and mutation coverage gaps. Refetch on matching hints and reconnect; reconcile overview inventory and snapshots at least every 15 seconds. There is no sequence, replay, durable cursor or atomic snapshot/event boundary. See x-blackhole.queue_live and BlackholeQueueLive* schemas for the machine-readable source profile.

Company queue overview and selected detail now have versioned source HTTP schemas and a linked invalidation contract. This is not a tested Next.js browser integration or historical API. Server-side resource permissions are required; downloading company-wide events and hiding other queues in the browser is not an authorization boundary. Clear old data and unsubscribe or reconnect when changing scope.

  1. Keep master/API credentials on the backend. If using a browser connection, provide only the authorized user's short-lived token through your approved authentication flow; never use a public build-time secret variable.
  2. Create the connection in a Client Component effect or a shared client-side connection manager, not during server rendering. Resolve a configured, allowlisted WSS URL. Do not automatically trust a URL supplied by a query parameter.
  3. On open, send the explicit bindings with a unique correlation ID. For queue-live, serialize subscriptions behind matching success ACKs. Use bounded pending-request timeouts and distinguish connected, subscribing, live and stale/error states.
  4. For queue-live, coalesce invalidations while fetching the authorized HTTP snapshot, then refetch if dirty. Do not buffer count deltas or replay hints as state. Native Blackhole has no atomic snapshot boundary or replay cursor; retain the 15-second reconciliation even while connected.
  5. On close, timeout, buffer overflow or ambiguity, mark data stale and reconnect with capped exponential backoff and jitter. Reauthenticate, resubscribe and fetch a fresh authoritative snapshot; never just restore the previous green status.
  6. Cancel retry/heartbeat/request timers and close the socket in effect cleanup, on logout and on account/user/token changes. React development effects may set up and clean up more than once; avoid duplicate connections and stale callbacks updating the new account's state.
  7. Keep supervision, queue edits and callback mutations on their documented authorized HTTP APIs. A WebSocket event is not authority to perform a mutation or proof that a supervision request connected.

Delivery limits and remaining ACDC work

The source patch sets blackhole.max_frame_size_bytes to 65,536 bytes by default, with an allowed integer range of 1–1,048,576. Invalid settings fall back to the default; changes apply to new connections. This bounds individual frames and reassembled fragmented messages, not total server memory or outbound traffic. A very small setting can reject legitimate subscriptions or legacy API messages. Close codes are 1003 for unsupported binary/non-object messages, 1007 for malformed or ambiguous JSON, and 1009 for oversize messages. Deployment acceptance is separate: this source reference does not prove that the running server has the patch. Treat protocol rejections as errors to correct, not requests to retry endlessly.

Call supervision is an HTTP command

Use POST /v2/accounts/{ACCOUNT_ID}/channels/{UUID}, documented under Call supervision in OpenAPI. Start with the target call leg and an authorized supervisor device_id. For whisper, select the agent leg. Do not send supervision as an invented WebSocket action.

Feature / actionRequired audio behavior
Listen / spy: eavesdropSupervisor hears both parties; neither party hears the supervisor.
whisperSupervisor hears the conversation and speaks to the selected agent only; customer cannot hear the supervisor.
barge / joinSupervisor, agent and customer hear one another.

202 Accepted is not an audio-connection confirmation. Keep the returned request_id and supervisor_call_id; stop monitoring using that supervisor leg, never the original call leg. There are no listen or spy action names. Prior isolated single-host audio checks do not certify cluster failover or production traffic; SUP-01–03 track release acceptance.

Native subscriptions are socket-local and best effort. The emitter may drop messages when its session mailbox exceeds the configured limit (default 50); even command replies can be dropped. There is no documented durable replay, global sequence, exactly-once delivery or guaranteed loss notification. A successful ping does not prove no events were lost. Authoritative reconciliation remains necessary; WebSockets are still the live transport, not replaced by polling-only screens.

Live queue snapshots and exact queue invalidation are source implementations; end-to-end rollout acceptance remains separate. Durable ordering, replay, complete mutation coverage and instant revocation are not claimed. Workforce metrics need durable records and explicit metric definitions; they cannot be reconstructed reliably from an unpersisted browser event stream.

Sources and deployment

Reviewed local sources include cb_websockets.erl, socket/context/event modules, bh_call.erl, bh_queue_live.erl, acdc_live_auth.erl, kapi_acdc_dashboard_events.erl and subscription/token authorizers. Exact source hashes are recorded in coverage.json. Installer defaults include Blackhole within the Kazoo apps node; it is an Erlang application, not a separate systemd unit.
